# RareSuSi UI/UX Must-Have Build Items

작성일: 2026-08-23  
대상: `JunctionXKorea` 웹 UI  
목적: 첨부된 Must-Have 기준을 현재 구현 상태와 비교해, 지금 만들어야 할 항목을 실행 가능한 단위로 정리한다.

---

## 1. 요약

현재 UI는 에이전트 캐릭터, 활성 상태, 활동 로그, 토큰/비용 표시의 기본 골격은 갖추고 있다. 다만 Must-Have 기준에서 중요한 “누가 누구에게 넘겼는지”, “왜 실패했는지”, “왜 다시 시도하는지”, “최종 답이 어떤 검증을 거쳤는지”는 아직 독립적인 데이터 모델과 화면 표현이 부족하다.

따라서 지금 만들어야 할 핵심은 다음 5개다.

1. 에이전트 간 핸드오프를 이벤트와 UI로 명시한다.
2. 실패 지점과 실패 원인을 분리해서 보여준다.
3. 재시도/분기 이유를 사용자가 이해할 수 있는 문장으로 표시한다.
4. 모델별 토큰/비용을 누적 비용 관점으로 정리한다.
5. 최종 답에서 검증 단계와 근거로 역추적할 수 있게 만든다.

---

## 2. 우선순위

| 우선순위 | 항목 | 이유 | 현재 상태 |
| --- | --- | --- | --- |
| P0 | 핸드오프 명시 | 협업 시각화의 핵심. 사용자가 “일이 흐른다”는 것을 이해해야 함 | 로그 순서로만 간접 표현 |
| P0 | 실패 지점 + 원인 분리 | “실패했다”보다 “어디서, 왜”가 중요함 | `issue`와 `reason`은 있으나 화면 연결 약함 |
| P1 | 재시도/분기 이유 표시 | 재시도 버튼만 있으면 사용자가 원인을 모름 | reset 동작만 있음 |
| P1 | 검증 역추적 | 최종 답의 신뢰도를 설명하는 핵심 장치 | `verify` 단계는 있으나 final trace 없음 |
| P2 | 모델별 누적 비용 | RareSuSi의 효율성 메시지를 정량적으로 보여줌 | 토큰/예상 비용은 있으나 모델별 구분 없음 |

## 3. 만들어야 할 것

### 3.1 에이전트 간 핸드오프

목표:

사용자가 특정 시점에 어떤 에이전트가 어떤 에이전트에게 작업을 넘겼는지 바로 볼 수 있어야 한다.

구현 항목:

- `handoff` 이벤트 타입 추가
- `fromAgentId`, `toAgentId`, `handoffReason`, `artifactName` 필드 추가
- 중앙 무대에서 에이전트 간 이동선 또는 pulse 표시
- 활동 로그에 “기준 작성자 -> 코드 작성자: 성공 조건을 넘겼어요” 형태로 표시
- 최근 핸드오프를 오른쪽 패널에 요약

예시 문구:

```text
기준 작성자가 코드 작성자에게 성공 조건을 넘겼어요.
검사자가 최종 판정자에게 검증 결과를 넘겼어요.
```

완료 기준:

- 화면에 `A -> B` 형태의 핸드오프가 최소 1곳 이상 명시된다.
- raw log를 보지 않아도 작업 전달 흐름을 이해할 수 있다.

---

### 3.2 실패 지점과 원인 분리

목표:

실패 이벤트를 단순 경고로 보여주지 않고, “실패한 위치”와 “실패 원인”을 분리해 보여준다.

구현 항목:

- `issue` 모델 확장
  - `failedAgentId`
  - `failedStepId`
  - `failurePoint`
  - `failureCause`
  - `rawTraceId`
- 중앙 무대에서 실패한 에이전트와 단계 강조
- 오른쪽 패널에 실패 요약 블록 추가
- “자세히 보기” 버튼에 실패 원인 패널 연결
- raw trace는 접힌 상세 영역으로 분리

예시 문구:

```text
실패 지점: 검사 단계
원인: 모델 호출 제한으로 검증 요청이 중단됐어요.
```

완료 기준:

- “문제 발생”만 보이는 상태가 아니라, 실패 위치와 원인이 각각 보인다.
- raw trace가 기본 화면을 덮지 않는다.

---

### 3.3 재시도/분기 이유 표시

목표:

사용자가 왜 다시 시도하는지, 왜 다음 에이전트로 넘어가는지 이해할 수 있어야 한다.

구현 항목:

- `retry` 또는 `branch` 이벤트 타입 추가
- `retryReason`, `retryStrategy`, `nextAgentId` 필드 추가
- 재시도 버튼 근처에 이유 표시
- 활동 로그에 재시도/분기 이벤트 추가
- 재시도 후 같은 실패가 반복됐는지 여부 표시

예시 문구:

```text
모델 호출 제한이 원인이어서 30초 뒤 같은 검증을 다시 시도해요.
검사 결과가 통과되어 최종 판정자로 넘겨요.
```

완료 기준:

- 사용자가 “왜 다시 누르는지” 알 수 있다.
- 재시도와 단순 초기화가 UI에서 구분된다.

---

### 3.4 모델별 누적 토큰/비용

목표:

에이전트별 토큰 사용량을 넘어서, 모델별 비용과 누적 비용을 보여준다.

구현 항목:

- 에이전트 데이터에 `modelName`, `modelTier`, `costKrw` 추가
- `ResourceSummary`에 모델별 집계 추가
- 오른쪽 패널에 모델별 비용 표 추가
- 전체 비용 progress를 실제 총합 기준으로 계산
- 1x/2x/3x 모델 구분 표시

예시 표시:

```text
1x 모델: 8.5k tokens / ₩420
2x 모델: 3.0k tokens / ₩300
3x 모델: 1.6k tokens / ₩480
누적 비용: ₩1,200
```

완료 기준:

- 사용자가 어떤 모델이 비용을 많이 쓰는지 알 수 있다.
- RareSuSi가 비용 효율을 관리한다는 메시지가 화면에서 보인다.

---

### 3.5 최종 답에서 검증 단계 역추적

목표:

최종 답이 그냥 완료된 것이 아니라, 어떤 검증 단계를 거쳐 신뢰할 수 있는지 확인할 수 있어야 한다.

구현 항목:

- `finalResult` 모델 추가
  - `answerSummary`
  - `verifiedBy`
  - `verificationSteps`
  - `sourceLogIds`
  - `confidenceLabel`
- 최종 판정자 카드에 검증 요약 표시
- 활동 로그와 검증 단계 연결
- 최종 결과 패널에서 관련 로그로 이동할 수 있게 구성
- `StepProgress`를 실제 화면에 연결해 단계명을 명확히 표시

예시 문구:

```text
최종 판정 완료
검증 근거: 검사자가 테스트 2개를 통과했고, 최종 판정자가 결과를 확인했어요.
```

완료 기준:

- 최종 답에서 검증 로그로 거슬러 올라갈 수 있다.
- 사용자가 완료 결과의 근거를 확인할 수 있다.

## 5. 추천 구현 순서

### 1차: 데이터 모델부터 고정

- `VisualizationState`에 `handoff`, `retry`, `finalResult` 추가
- `issue`를 실패 지점/원인 구조로 확장
- mock replay에 대표 이벤트 1개씩 추가

### 2차: 화면에 최소 표현 연결

- 중앙 무대에 핸드오프 표시
- 오른쪽 패널에 실패 원인과 재시도 이유 표시
- `StepProgress`를 화면에 연결

### 3차: 비용/검증 신뢰도 강화

- 모델별 비용 표 추가
- 최종 결과와 검증 로그 연결
- 활동 로그에서 관련 이벤트를 따라갈 수 있게 정리

### 4차: polish

- 핸드오프 motion
- 실패 상태 microinteraction
- 재시도 후 회복 상태 표현
- 문구 톤 통일

## 6. MVP 완료 기준

다음 질문에 화면만 보고 답할 수 있으면 MVP 기준을 충족한다.

- 지금 어떤 에이전트가 일하고 있는가?
- 방금 일이 누구에게서 누구에게 넘어갔는가?
- 실패했다면 어디에서 왜 실패했는가?
- 다시 시도한다면 왜 다시 시도하는가?
- 지금까지 모델별로 비용을 얼마나 썼는가?
- 최종 답은 어떤 검증 단계를 거쳤는가?

가장 작은 다음 구현 단위는 다음이다.

1. `VisualizationState.currentHandoff` 추가
2. `VisualizationState.issue`를 `failurePoint`/`failureCause` 구조로 확장
3. `ReasonPanel`을 실제 화면에 연결
4. `StepProgress`를 중앙 무대 아래에 연결
5. `AgentResourcePanel`의 “자세히 보기” 버튼을 실패 상세 토글로 변경

이 5개만 해도 Must-Have 적용도는 현재 약 45~50%에서 약 70% 수준까지 올라갈 수 있다.
