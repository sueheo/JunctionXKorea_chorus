# RareSuSi Frontend Plan

작성일: 2026-08-23  
대상 Repository: `sueheo/JunctionXKorea`  
목적: JunctionX Korea 제출용 인터랙티브 웹 프론트엔드 구현 방향 정리

---

## 1. 현재 상황

현재 `JunctionXKorea` Repository는 거의 빈 템플릿 상태다.

- 기존에 만든 `dugaza` 웹은 테스트용이므로 더 이상 고려하지 않는다.
- 이 Repository 안에는 아직 실제 프론트엔드 앱 구조가 없다.
- Figma Hi-Fi 디자인은 별도로 준비 중이며, 2026-08-23 기준 하이파이 초안 이미지가 공유되었다.
- 현재 가장 구체적인 UI 기준 문서는 `RareSuSi_캐릭터_UI_디자인_정리.md`다.
- GO / AI:GO Squad의 실제 이벤트 로그 일부는 확인 가능하지만, 최종 API나 Event Schema로 확정된 상태는 아니다.

따라서 지금 단계의 핵심은 바로 구현을 시작하는 것이 아니라, 먼저 웹의 방향과 MVP 범위를 명확히 고정하는 것이다.

---

## 2. 프로젝트 목표

RareSuSi 웹은 단순한 개발자용 로그 대시보드가 아니다.

목표는 다음과 같다.

> AI나 개발을 잘 모르는 사용자도, 여러 AI Agent가 하나의 문제를 해결하기 위해 어떻게 역할을 나누고 협업하는지 직관적으로 이해할 수 있게 만드는 인터랙티브 시각화 웹

사용자가 화면에서 이해해야 하는 내용은 다음이다.

- 지금 어떤 Agent가 일하고 있는가?
- 각 Agent는 어떤 역할을 맡고 있는가?
- 일이 누구에게서 누구에게 전달되고 있는가?
- 전체 문제 해결 과정이 어느 단계까지 진행되었는가?
- 실패나 재시도가 있다면 어디서 왜 발생했는가?
- 최종 결과가 어떤 협업 과정을 거쳐 만들어졌는가?

## 3. 핵심 UX 방향

RareSuSi의 시각화 콘셉트는 **오케스트라 무대**다.

개발자용 raw log를 그대로 보여주는 대신, Agent들의 역할과 상태를 캐릭터의 표정, 자세, 움직임, 말풍선, 진행선으로 번역한다.

예를 들어 raw event가 다음과 같더라도:

```text
squad:task-status-changed
agent-state-changed: running
```

사용자에게는 다음처럼 의미 중심으로 표현한다.

```text
코드 작성자가 의심스러운 부분을 수정하고 있어요.
검사자가 첫 번째 결과를 확인하고 있어요.
최종 판정자가 제출해도 되는지 보고 있어요.
```

중요 원칙:

- 중앙 화면은 표나 로그가 아니라 Agent 캐릭터가 있는 열린 무대다.
- 로그는 보조 정보이며 왼쪽 접이식 패널에 둔다.
- 상세 수치와 근거는 오른쪽 패널에 둔다.
- 중요한 사건만 말풍선으로 잠깐 보여준다.
- 기술적인 표현보다 사용자가 이해할 수 있는 문장을 우선한다.

## 4. 초기 MVP 화면 구조

첫 번째 구현은 하나의 핵심 화면에 집중한다.

### 4.1 중앙 무대

중앙에는 카드나 박스로 감싸지 않은 열린 무대를 둔다.

표현 요소:

- 진행 관리자
- 기준 작성자
- 코드 작성자
- 검사자
- 최종 판정자
- 현재 전체 상태 한 문장
- Agent 간 작업 전달 모션
- 현재 단계 진행선

중앙 무대에서 항상 보여줄 정보:

- 캐릭터
- 역할 이름
- 현재 상태
- 중요한 사건 말풍선

### 4.2 왼쪽 활동 로그

왼쪽 패널은 접고 펼 수 있어야 한다.

역할:

- 방금 지나간 사건 기록
- Agent별 주요 행동 히스토리
- 실패, 재시도, 완료 이벤트 확인

주의:

- raw log 전체를 그대로 노출하지 않는다.
- 사용자 친화적인 문장으로 변환된 로그를 보여준다.

### 4.3 오른쪽 Agent 상세 패널

캐릭터를 클릭하면 오른쪽 패널에서 해당 Agent의 상세 정보를 보여준다.

포함 가능 정보:

- Agent 이름
- 역할 설명
- 현재 상태
- 최근 수행한 일
- 사용 모델
- 토큰 사용량
- 비용 추정
- 최근 이벤트

### 4.4 하단 진행선

큰 카드 여러 개 대신 간결한 단계 진행선을 사용한다.

초기 단계 예시:

```text
문제 찾기 -> 기준 세우기 -> 수정하기 -> 검사하기 -> 최종 판정
```

완료된 단계, 현재 단계, 다음 단계를 명확히 구분한다.

## 5. Hi-Fi Draft 기준 화면 정리

2026-08-23에 공유된 하이파이 초안은 현재 구현할 웹의 가장 직접적인 시각 기준이다.
세부 디자인은 바뀔 수 있지만, 전체 정보 구조와 사용자 경험 방향은 이 초안을 우선 참고한다.

### 5.1 전체 레이아웃

초안은 다음 5개 영역으로 구성된다.

| 영역 | 역할 | 구현 우선순위 |
| --- | --- | --- |
| 상단 실행 바 | 프로젝트 선택, 실행 상태, 단계 수, 경과 시간, 일시정지/중지 | 높음 |
| 왼쪽 Easy activity log | 비전공자도 읽을 수 있는 쉬운 활동 기록 | 높음 |
| 중앙 협업 무대 | Agent 캐릭터와 현재 협업 상태를 가장 크게 표현 | 매우 높음 |
| 오른쪽 에이전트와 자원 | Agent별 상태, 토큰 사용량, 비용, 문제 상태 | 높음 |
| 하단 설명 영역 | 현재 상황을 쉬운 문장으로 해석 | 중간 |

이 구조는 일반적인 관리자 대시보드가 아니라, **데모 실행 상황을 실시간으로 이해하는 관찰 화면**에 가깝다.

### 5.2 상단 실행 바

상단은 사용자가 현재 데모 실행 상태를 한눈에 이해하는 영역이다.

포함 요소:

- RareSuSi 로고와 서비스명
- 프로젝트 선택 드롭다운
- 전체 실행 상태 배지
- 현재 단계 수
- 경과 시간
- Pause 버튼
- Stop 버튼

초기 MVP에서는 실제 실행 제어가 아니라 replay 제어로 동작해도 된다.
다만 사용자에게는 실행 중인 Squad를 관찰하고 있다는 느낌을 줘야 한다.

### 5.3 왼쪽 Easy activity log

왼쪽 패널은 기술 로그가 아니라 쉬운 활동 로그다.

구성 요소:

- 전체 / 진행 / 완료 / 문제 필터
- 시간 그룹
- Agent 아바타
- 사용자 친화적인 한 줄 설명
- 상태 아이콘
- 기술 로그 보기 버튼
- Agent 아이콘 클릭 안내

중요 원칙:

- raw event name을 그대로 보여주지 않는다.
- "검사자가 첫 번째 테스트를 통과시켰어요"처럼 행동 의미를 보여준다.
- 기술 로그는 기본 화면에서 분리한다.
- Agent 아이콘을 클릭하면 해당 Agent 기준으로 로그를 필터링할 수 있게 한다.

### 5.4 중앙 협업 무대

중앙은 가장 중요한 화면이다.

초안 기준 핵심 요소:

- 제목: 현재 협업 무대
- 정보 아이콘
- 전체 상태 문장
- 2단 무대
- 캐릭터 5명
- 별도 지휘자 캐릭터
- 캐릭터 아래 역할명
- 하단 단계 진행선
- 현재 상황 설명 패널

초기 구현에서는 최종 캐릭터 에셋이 없을 수 있으므로 placeholder를 사용할 수 있다.
하지만 layout, hierarchy, role placement는 초안에 가깝게 유지한다.

중앙 무대 배치 초안:

```text
상단 단상: 진행 관리자, 기준 작성자
하단 단상: 코드 작성자, 검사자, 최종 판정자
전면: 지휘자
```

중앙 상태 문장 예시:

```text
코드 수정과 검증이 동시에 진행 중이에요
```

### 5.5 오른쪽 에이전트와 자원 패널

오른쪽 패널은 Agent별 상세 상태와 자원 사용량을 확인하는 영역이다.

Agent 카드 구성:

- 캐릭터 썸네일
- Agent 이름
- 쉬운 역할 설명
- 상태 배지
- 토큰 사용량
- 토큰 진행 바
- 도움말 아이콘

하단 자원 요약:

- 전체 토큰
- 토큰 한도 대비 사용량
- 예상 비용
- 상태 아이콘 안내
- 문제 발생 경고 박스
- 자세히 보기
- 다시 시도

초기 MVP에서는 토큰과 비용을 mock data로 표시한다.
실제 GO 연동 전까지는 "예상" 또는 "샘플" 성격임을 내부적으로 구분한다.

### 5.6 하단 설명 영역

하단 설명 영역은 사용자가 "왜 이 Agent가 깨어났는지" 이해하게 만드는 영역이다.

초안 문구 방향:

```text
왜 이 에이전트가 깨어났나요?
검사자가 테스트 중 문제를 발견했어요. 코드가 그 부분을 고치는 동안, 기준과 진행 관리자가 다음 단계를 준비했어요.
```

이 영역은 단순 로그보다 더 교육적이다.
멀티 에이전트 시스템을 모르는 사용자가 Agent 협업의 이유를 이해하도록 돕는다.

### 5.7 우선 컴포넌트 분해

구현 시 우선 컴포넌트는 다음과 같이 나눈다.

| Component | 역할 |
| --- | --- |
| `TopRunBar` | 로고, 프로젝트 선택, 실행 상태, 시간, 제어 버튼 |
| `ActivityLogPanel` | 쉬운 활동 로그와 필터 |
| `LogGroup` | 시간 단위 로그 그룹 |
| `StageHeader` | 중앙 제목과 전체 상태 문장 |
| `CollaborationStage` | 2단 무대와 캐릭터 배치 |
| `AgentCharacter` | 캐릭터, 상태, 역할명, 클릭 영역 |
| `StepProgress` | 하단 단계 진행선 |
| `ReasonPanel` | 왜 Agent가 깨어났는지 설명 |
| `AgentResourcePanel` | 오른쪽 Agent 카드 리스트 |
| `AgentResourceCard` | Agent별 상태와 토큰 |
| `ResourceSummary` | 전체 토큰과 예상 비용 |
| `IssueAlert` | 문제 발생, 자세히 보기, 다시 시도 |

초기에는 복잡한 전역 상태 관리 없이 상위 `App` 또는 `ReplayController`에서 state를 내려주는 방식으로 시작한다.

### 5.8 구현 시 주의할 점

- 초안의 밝고 부드러운 제품형 UI 느낌을 유지한다.
- 중앙 무대는 여전히 화면의 주인공이어야 한다.
- 왼쪽과 오른쪽 패널은 정보 보조 역할로 둔다.
- 카드가 많지만, 중앙 무대를 또 다른 카드처럼 가두지 않는다.
- 기술 로그와 쉬운 로그를 명확히 분리한다.
- Pause / Stop은 MVP에서 replay control로 먼저 구현할 수 있다.
- 캐릭터 에셋은 최종본이 오기 전까지 교체 가능한 구조로 둔다.
- 모바일 대응은 첫 MVP 이후 조정하되, desktop demo 화면은 먼저 안정화한다.

## 6. Agent 구성 초안

현재 디자인 문서 기준 Agent / 캐릭터는 다음과 같다.

| Agent | 사용자에게 보이는 역할 | 주요 상태 표현 |
| --- | --- | --- |
| 진행 관리자 | 전체 작업 흐름을 조율 | 헤드셋, 오케스트레이션 |
| 기준 작성자 | 문제와 판단 기준 정리 | 클립보드, 연필 |
| 코드 작성자 | 의심 영역 수정 및 해결안 작성 | 안경, 코드 작업 소품 |
| 검사자 | 반례와 오류 탐색 | 안테나, 돋보기 |
| 최종 판정자 | 제출 가능 여부 판단 | 도장, 승인 제스처 |

추가로 전체 오케스트레이션을 상징하는 지휘자 캐릭터가 필요할 수 있다.
다만 MVP에서는 진행 관리자와 지휘자 역할이 겹치지 않도록 먼저 화면 구조를 단순화한다.

## 7. 상태 시스템

모든 Agent는 동일한 5가지 상태를 가진다.

| 상태 | 의미 | UI 표현 |
| --- | --- | --- |
| idle | 대기 중 | 잠자기 또는 가벼운 호흡 |
| ready | 기본 상태 | 정면 응시, 약한 미소 |
| working | 작업 중 | 소품 사용, 작은 반복 모션 |
| completed | 완료 | 뿌듯한 표정, 짧은 체크 효과 |
| error | 실패 | 절망한 표정, 짧은 실패 효과 |

상태 표현은 아이콘이나 텍스트보다 캐릭터의 표정과 자세로 먼저 읽히는 것을 목표로 한다.

## 8. 데이터 흐름 원칙

UI 컴포넌트가 GO Squad raw event를 직접 읽지 않도록 한다.

기본 구조:

```text
Mock / Replay Squad Event
        ↓
Squad Event Adapter
        ↓
Visualization State
        ↓
UI Components
```

나중에 실제 연동이 가능해지면 다음 구조로 교체한다.

```text
GO / AI:GO Squad Event
        ↓
Squad Event Adapter
        ↓
Visualization State
        ↓
UI Components
```

이렇게 분리하는 이유:

- 실제 GO event schema가 아직 확정되지 않았다.
- 데모 상황에서 실시간 연동이 실패해도 Replay mode는 작동해야 한다.
- UI는 사용자 경험에 집중하고, raw data 해석은 adapter에서 처리해야 한다.

## 9. MVP 데이터 전략

초기 구현은 실제 API 연동이 아니라 **Mock / Replay 기반**으로 만든다.

MVP에서 필요한 mock data:

- Agent 목록
- Agent별 역할 설명
- 단계 목록
- 시간순 이벤트 목록
- 이벤트별 Agent 상태 변화
- 이벤트별 말풍선 문장
- 토큰 / 비용 예시
- 성공 / 실패 / 재시도 시나리오

실제 GO 로그에서 확인한 이벤트 예시:

```text
squad:planning-started
squad:plan-ready
squad:execution-started
squad:task-wave-started
squad:task-status-changed
squad:agent-state-changed
squad:task-completed
squad:aggregation-started
squad:execution-completed
```

단, 이 이벤트 목록은 참고용이다.
아직 최종 스키마로 확정하지 않는다.

---

## 10. 기술 스택 확정

확정 기술 스택:

```text
Vite + React + TypeScript
```

선택 이유:

- 캐릭터 상태, replay, 패널 선택 상태를 관리하기 쉽다.
- 컴포넌트 단위로 Figma 디자인을 반영하기 좋다.
- 추후 실제 Squad adapter를 붙이기 쉽다.
- 해커톤 데모와 GitHub 제출에 적합하다.

초기에는 별도 백엔드 없이 프론트엔드 정적 앱으로 시작한다.

추후 실제 GO 연동이 필요해지면:

- local JSON replay
- 파일 업로드 기반 replay
- local dev server API
- WebSocket / SSE

중 하나를 실제 가능성에 따라 선택한다.

## 11. 구현 우선순위

### Phase 1. 방향 문서화

- 현재 문서 작성
- MVP 범위 합의
- 화면 구조 합의
- 기술 스택을 `Vite + React + TypeScript`로 확정
- 하이파이 초안 기준 컴포넌트 구조 반영

### Phase 2. 프로젝트 스캐폴딩

- Vite + React + TypeScript 프로젝트 생성
- 기본 폴더 구조 정리
- 실행 스크립트 설정
- README 초안 업데이트

### Phase 3. Static UI

- 전체 레이아웃 구현
- 상단 실행 바 구현
- 중앙 오케스트라 무대 구현
- 왼쪽 로그 패널 구현
- 오른쪽 상세 패널 구현
- 하단 진행선 구현
- 하단 설명 패널 구현

### Phase 4. Mock Replay Prototype

- mock event data 작성
- adapter 작성
- 재생 / 일시정지 / 다시보기 구현
- Stop / retry 상태 처리
- 이벤트에 따라 Agent 상태 변화
- 말풍선과 로그 동기화
- 토큰 / 비용 mock state 동기화

### Phase 5. Visual Polish

- Figma Hi-Fi 디자인 반영
- 캐릭터 에셋 교체
- 상태 모션 추가
- 반응형 레이아웃 조정

### Phase 6. GO Integration Spike

실제 GO / AI:GO 로그와 연결 가능한지 조사한다.

확인 항목:

- Agent 시작 / 종료
- Agent 상태
- Task 시작 / 완료
- Agent 간 메시지
- Tool call
- 실패 / 재시도
- token usage
- timestamp
- streaming 가능 여부

확인되지 않은 항목은 구현된 것처럼 표현하지 않는다.
